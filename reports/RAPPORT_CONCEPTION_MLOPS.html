1. PARTIE II — QCM D'ÉVALUATION (15 points)

Q1. Séquence correcte des étapes en production

Réponse : B. Ingestion des données → Entraînement du modèle → Déploiement → Monitoring

Justification : La chaîne de valeur canonique débute par la collecte et l'ingestion des flux de données validées, suivies par la phase d'entraînement et d'évaluation, puis par le serving de l'inférence. Le monitoring intervient en aval pour observer le comportement réel et piloter le réentraînement continu.

Q2. Artefacts supplémentaires versionnés par le MLOps

Réponse : B. Les données d'entraînement et les artefacts de modèle

Justification : En ingénierie logicielle classique, le code seul produit le binaire. En apprentissage automatique, le binaire est le produit indissociable du code et des données. Le MLOps exige le versioning rigoureux des jeux de données (DVC) et des modèles sérialisés (MLflow Model Registry).

Q3. Pratique garantissant le plus directement la reproductibilité

Réponse : C. Fixer les graines aléatoires, la version des données, le commit de code et les dépendances

Justification : La reproductibilité scientifique et réglementaire n'est assurée que si le quadruplet {commit Git, hash des données DVC, environnement scellé, graine pseudo-aléatoire seed=42} est figé de bout en bout.

Q4. Rôle des quatre couches « logs, métriques, traces, alertes »

Réponse : B. À assurer l'observabilité technique et comportementale du système en production

Justification : Les logs enregistrent l'historique d'inférence avec pseudonymisation, les métriques suivent la latence et le PSI, les traces décomposent les goulots d'étranglement microservices, et les alertes automatisent l'escalade vers les équipes d'astreinte.

Q5. Objectif principal du Model Registry (registre de modèles)

Réponse : B. Gérer les versions des modèles, leur statut (staging/production) et les métadonnées associées

Justification : Le registre centralise les artefacts sérialisés, trace leur lignage (paramètres, matrice de confusion) et sépare le candidat validé (Staging / Challenger) du service actif (Production / Champion).

Q7. Data Drift vs Concept Drift dans le scoring télécom (6 pts)

Formulation formelle : Le Data Drift correspond à la dérive des distributions d'entrée \(P(X)\) à relation \(P(Y|X)\) constante. Le Concept Drift désigne la rupture de la relation fonctionnelle \(P(Y|X)\), avec ou sans dérive de \(P(X)\).
  • Data Drift (Exemple Télécom) : Une inflation forte au Nigeria entraîne une augmentation brutale des dépenses moyennes (avg_monthly_spend_ngn × 1.6) et une raréfaction des recharges. Le profil d'entrée a dérivé, mais les clients dépensiers restent solvables. Détectable en temps réel à l'inférence via le PSI et le test KS sans attendre les étiquettes.
  • Concept Drift (Exemple Télécom) : Une crise de liquidité bancaire frappe le pays. Des clients ayant un comportement d'usage exemplaire (late_payment_count = 0, régularité élevée) cessent subitement d'honorer leurs factures. Les variables d'entrée restent parfaitement stables, mais le risque d'impayé explose. Détectable uniquement lorsque les étiquettes de remboursement réelles remontent à J+30 (chute brutale du F1-score et du rappel de la classe high).

Q8. Stratégie de redéploiement sécurisée, Canari et Rollback (6 pts)

Le déploiement d'une nouvelle version de modèle applique une progression stricte en 3 phases :

  1. Mode Miroir (Shadow Deployment) : Le nouveau modèle (Challenger) reçoit une copie en direct des requêtes sans impacter les clients. Cette étape valide la latence, la stabilité mémoire et l'absence de crash.
  2. Déploiement Canari (Canary Deployment) : L'Ingress Controller achemine 5% du trafic vers le conteneur Challenger et 95% vers le Champion. L'observabilité Prometheus vérifie l'absence d'erreurs 5xx et la tenue de la latence (< 150 ms). Le trafic passe progressivement à 20%, 50%, puis 100%.
  3. Critères d'automatisation du Rollback : Le retour immédiat au modèle précédent est déclenché sans délai si :
    • La latence p95 dépasse 300 ms pendant plus de 3 minutes consécutives.
    • Le taux d'erreurs HTTP 5xx dépasse 0,5% des requêtes.
    • La part des prédictions de classe high dépasse 60% (signal d'incompatibilité de schéma).

ii. Architecture du Pipeline CI / CD / CT (6 pts)

  • Pipeline CI (Intégration Continue) : Déclenché sur chaque Pull Request et push sur master. Installe l'environnement, exécute le linter ruff check (0 avertissement) et lance les 25 tests unitaires automatisés (API, Pydantic, prétraitement, fonctions de calcul de PSI).
  • Pipeline CD (Déploiement Continu) : Après validation des tests CI, GitHub Actions compile l'image Docker, exécute un Smoke Test en lançant le conteneur en arrière-plan pour sonder /health et /metrics, puis pousse l'artefact sur GitHub Container Registry (ghcr.io) et Docker Hub.
  • Pipeline CT (Entraînement Continu) : Déclenché par la consolidation des étiquettes à J+30 ou de manière planifiée chaque mois. Entraîne un modèle Challenger dans un espace isolé, le soumet à la Porte de Qualité mathématique, et le référence dans MLflow.

iv. Gestion du Cycle de Vie, Gouvernance & Auditabilité (5 pts)

  • Traçabilité Intégrale : Chaque prédiction est traçable jusqu'au commit Git du code, au hash MD5 des données d'entraînement DVC, et à la version du conteneur Docker.
  • Conformité NDPR (Nigeria Data Protection Regulation) / RGPD :
    • La colonne phone_number présente dans les données brutes est systématiquement éliminée dès l'audit pour proscrire toute PII (donnée personnelle identifiable).
    • L'identifiant customer_id est pseudonymisé à la volée par hachage cryptographique non réversible : SHA256(customer_id)[:16].
  • Défendabilité des Décisions : L'utilisation d'arbres de décision XGBoost avec valeurs de Shapley (SHAP) permet de justifier auprès du régulateur financier nigérian les motifs précis d'un refus de crédit.
